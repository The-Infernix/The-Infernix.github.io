Debugging Browser-Based ML Inference: Lessons from ONNX Runtime Web

Running MobileViT inside a browser extension means WebGPU when you can get it, WASM when you can't, and failure modes that only exist at the intersection. This is what broke, what the breakage looked like from the outside, and how it was pinned down.

Pavan Ganesh Indupudi (Infernix) Published 2026-10-21 13 min read

CONTENTS

    PRIVYSE runs a quantized MobileViT-Small inside the browser — not on a server, not in a worker talking to a GPU daemon, but through ONNX Runtime Web in the extension itself. The model classifies screenshot tiles so the privacy pipeline knows which regions need Tier C protection.

    This article is about the part of that work that does not fit in a README: the failure paths. Most of them are documented in the repository's own perception failure-path audit, and two of them were genuinely surprising. One was a batched inference bug that silently corrupted every tile it touched while looking, from the outside, like a model that was merely unsure. The other was a timeout budget that let the least important pass starve the two that mattered most.

    Both are written up here with the numbers they produced, because a failure-mode write-up that omits the magnitudes is just a list of things that went wrong.

    The setup

    Everything below is taken from the PRIVYSE repository, so it can be checked line by line:

    • Model: MobileViT-Small (ImageNet-224/256 pretrained), quantized to q8 ONNX — model_quantized.onnx, 6,303,767 bytes (6.3 MB), bundled under extension/public/models/perception/. No CDN downloads, ever.
    • Runtime: ONNX Runtime Web with the WebGPU execution provider first. The bundled ort-wasm-simd-threaded.jsep.wasm (26.5 MB) is a dual runtime — it serves the WebGPU EP and the WASM EP from one binary — so a machine without a GPU drops to WASM without re-downloading anything. numThreads = 1 keeps it on the main thread: no SharedArrayBuffer, no cross-origin isolation headers.
    • Preprocessing: resize the tile's shortest edge to 288, center-crop 256, rescale by 1/255, normalize to [-1, 1], flip RGB → BGR — mirroring MobileViTFeatureExtractor.
    • Host context: Chrome MV3 service workers have no DOM, so the vision stack (MobileViT + BlazeFace + Tesseract.js) runs in a hidden offscreen document. Firefox MV2 has neither the offscreen API nor the side panel API — the background page is the DOM host, sharing the same core/vision-host.ts.
    • Visibility: the active provider is surfaced live in the side panel resource meter (perception · ⚡ WebGPU / wasm) and reported in perception stats alongside tile tags.
    • Caching: a pixel-hash map reuses the tile map when the page has not visually changed — cached perception reports ms: 0 against roughly 1.2–1.6 s for a fresh ViT pass. Faces, OCR, and the privacy gate still run fresh every step.
    typescript — WebGPU-first session creation, from extension/core/perception.ts 
    if (webgpuAvailable()) {
  try {
    session = await createSession(ort, model, ["webgpu", "wasm"]);
    activeBackend = "webgpu";

The ["webgpu", "wasm"] provider list is what lets a single session fall through individual kernels to the WASM EP; the catch branch is the whole-session fallback if the WebGPU EP fails to initialise at all.

    Failure mode 1 — the batched input that corrupted every tile

    This is the one that should have shipped. The obvious optimisation for a vision model running on a grid of tiles is to stack them into one batched tensor and run a single inference instead of one per tile. It is faster, it is idiomatic, and it is exactly what we would have written.

    The A/B probe told a different story. On onnxruntime-web 1.29 with a WASM backend, a batched input of shape [N, 3, 256, 256] returned degraded logits — every tile pinned at roughly 22–33% confidence and mapped to the wrong class. The same batches run through onnxruntime-node were bit-exact. And a batch=1 run on the web backend matched the native reference exactly, tile by tile, in benchmarks/probe-batch.mjs.

    So the bug was not in the model, the preprocessing, or the browser. It was in one runtime's batched-input path. The uncomfortable part is that it did not crash and did not look like garbage — it looked like low confidence.

    typescript — the confidence bands, from extension/core/perception.ts 
    export function tagForClass(cls: number, conf: number): PerceptionTag {
  if (conf < 0.22) return "blank";
  if (conf < 0.5) return "uncertain";
  return TAG_OF_CLASS[cls] ?? "photo";
}

    Follow the arithmetic. A corrupted batch produces ~22–33% confidence, which lands inside the uncertain band. And uncertain is not a neutral state in this pipeline — it escalates:

    typescript — how an uncertain tile is handled, from extension/core/perception.ts 
    } else if (dom.tag === "uncertain") {
  escalate.push({
    region,
    tags,
    reason: `on-device ViT: low-confidence graphic (${dom.label}) — redacted conservatively`,
  });
  captchaLike.push({ region, tags, reason: "possible human-verification graphic (manual step)" });
}
    What the batch bug actually caused

    Two failure directions at once, from the same corrupted tensor. Tiles that fell below 0.22 collapsed to blank — a real photograph was never escalated, which is a missed redaction. Tiles that landed in the uncertain band were escalated and flagged as captchaLike, which is over-redaction plus false human-verification prompts sent to a human in the loop. Neither is a crash; both are wrong in a way that only shows up as a diff in aggregate behaviour. That is what "mis-escalated regions" and "turned real photos into uncertain/blank" meant in the audit: the model's sensitivity to real imagery was destroyed in both directions at once.

    The resolution was to give up the optimisation. Perception stays at batch=1 per tile, documented in perception.ts::classifyCanvas, and _abTest() is retained as a regression tripwire — it runs batched and single-tile inference over the same crops on one machine so a future onnxruntime-web upgrade that re-breaks the batch path fails loudly instead of silently. The latency win that the batch was supposed to buy came from somewhere else entirely, which is the next failure mode.

    Lesson

    A performance optimisation that produces plausible but wrong numbers is more dangerous than one that produces errors, because every downstream threshold you set will quietly calibrate itself around the corruption. When a cross-runtime A/B disagrees, believe the disagreement over your intuition about which side is "obviously right".

    Failure mode 2 — the pass that ate the budget

    The original design ran perception serially inside the vision pipeline: a 15-second inner timeout for the ViT, against a shared 30-second vision budget that faces and OCR also drew from. A hung or slow MobileViT could therefore consume half the total budget, and in the worst case cause faces and OCR to be skipped.

    That is a fail-open direction, and it is the kind that matters here: faces and OCR are the layers that perception is supposed to be backstopping. Letting the backstop consume the budget of the primary layers inverts the safety ordering.

    The fix was to make the three passes genuinely independent — each individually bounded, none able to starve the others — and to change the arithmetic of the whole pipeline from a sum to a maximum:

    typescript — concurrent, individually-bounded passes, from extension/core/vision.ts 
    const pass = {
  perception: (async () => {
    try {
      const p = await withTimeout(
        perceiveScreen({ imageDataUrl, imageRegions, budgetMs: 2500, maxTiles: 6, pageUrl }),
        7000,
        "perception-timeout",
      );
      out.perception = p;
    } catch (e) {
      stats.skipped.push("perception:" + errMsg(e));
    }
  })(),
  faces:  (async () => { /* withTimeout(…, 10000, "face-timeout") */ })(),
  ocr:    (async () => { /* withTimeout(…, 12000, "ocr-timeout")  */ })(),
};

await Promise.all([statsMB, pass.perception, pass.faces, pass.ocr]);

    Wall-clock vision latency is now max(perception, faces, OCR) instead of their sum, the ViT's inner timeout dropped from 15 s to 7 s, and a failure in any single pass is recorded in stats.skipped while the others complete untouched. Perception is best-effort by construction: it never blocks, never runs first, and its escalation decisions are purely additive to the sanitizer's redaction set.

    Design decision

    Escalation is additive, never subtractive. A missed perception decision means fewer redactions, but every other layer — DOM sweep, tokenizer, OCR, face detection, zero-leak gate — remains fully in force. That is what turns "perception failed" from a privacy incident into a performance event. Every row in the failure catalogue below inherits this property, and it is the reason the audit's verdict could be "no fail-open leak path" rather than "no fail-open path found so far".

    Failure mode 3 — the provider badge is a session label, not a measurement

    The side panel shows perception · ⚡ WebGPU or perception · wasm. It is a genuinely useful diagnostic, and it is also slightly less than it appears to be. Three details from the source are worth stating plainly.

    Detection is presence-only. webgpuAvailable() checks that navigator.gpu is defined — documented in-source as Chrome 113+ and Firefox 141+. The application code never calls requestAdapter() itself; adapter acquisition happens inside ORT's execution-provider initialisation, during InferenceSession.create. So there is no separate "adapter unavailable" state in the code — an adapter failure surfaces as a session-creation throw, and the catch branch retries on WASM using the same JSEP binary.

    The fallback is free. Because one binary serves both providers, dropping from WebGPU to WASM re-downloads nothing and re-initialises no weights. A user on a machine without a GPU pays no network penalty for the machine that has one.

    The badge describes the session, not the kernels. activeBackend is set to "webgpu" the moment session creation succeeds with the WebGPU EP in the provider list. Individual operators that the WebGPU EP does not support fall through to the WASM EP inside that same session — and the UI keeps reporting ⚡ WebGPU. There is no per-kernel accounting in the codebase and no partition-boundary logging.

    What this means for the badge

    Read ⚡ WebGPU as "the WebGPU EP owns this session", not as "every operator ran on the GPU". For a model like MobileViT — a transformer with a long operator tail — partial fallback is plausible in principle. We have not measured it, and the code does not currently let us: there is no GPU-path latency measurement on the same page, and no partition log to attribute per-op time. The honest statement is that the badge is session-scoped, and that the per-operator picture is a real gap rather than a solved question.

    Failure mode 4 — what the cache actually keys on

    The same-page cache exists because multi-step tasks re-visit the same screen constantly — typing into a form, paging a list. Re-running the ViT over byte-identical pixels burns battery and latency for nothing. The design goal was that a cached map is served only when the visible pixels are genuinely unchanged.

    Here is exactly what that means in the implementation. The screenshot is downscaled to 64×64 on a canvas, then an FNV-1a hash is computed over quantized luma samples taken every fourth pixel — about 256 samples — and rendered base-36. The cache key is:

    text — the cache key shape, from extension/core/perception.ts 
    cacheKey = `${pageUrl}#${img.naturalWidth}x${img.naturalHeight}#${regionsKey(...)}#${hash}`;

    A hit therefore requires the URL, the viewport size, and the non-DOM region list to match as well as the hash — which is what makes it conservative rather than merely fast. A scroll, a hover, a spinner, a cursor blink, a canvas redraw all change the sampled luma and produce a miss.

    Three corrections to assumptions I had going in, all confirmed by reading the code:

    The cache is not an LRU

    It is a plain Map capped at CACHE_MAX = 6, and on overflow it deletes perceptionCache.keys().next().value — the oldest inserted key. Entries are not re-inserted on a hit, so the eviction order is insertion order. It behaves like a small FIFO, not an LRU. Under a workload that touches seven distinct pages, the first one is gone.

    The hash samples luma, not colour

    Because the FNV-1a input is 0.299R + 0.587G + 0.114B, two visually different frames with identical luminance at every sampled point hash the same. A colour-only change on a large flat surface can survive all 256 samples. No such false hit has been observed in the benchmark suite, but it is a real class of blind spot rather than a hypothetical one, and it is the first thing to check if a cached map ever serves stale tiles.

    The cache never touches the privacy layers

    The cache short-circuits perceiveScreen and nothing else. Faces, OCR, the DOM sweep, the tokenizer, and the zero-leak gate run fresh on every single step, cached map or not. The cache is also opt-in: it only engages when the caller passes pageUrl (the extension passes the tab URL; the agent loop in the bench harness passes location.href). With no pageUrl, there is no caching at all.

    The failure catalogue

    The audit enumerated every failure point and asked one question of each: does anything sensitive still travel? The table is the useful artifact — it is what "fail-closed" actually means when you have to defend it.

    #Failure modeConsequenceFail-open?

    2WASM unavailable / bundle missing (stale build, file:// page)Same degrade pathNo

    The catalogue resolves into two shapes. Rows 1–3 are fail-closed: the perception pass degrades to nothing and every other layer stays in force. Rows 5–6 are bounded: a partial grid means missing additive decisions, while faces and OCR cover the non-DOM regions regardless of tiling. Row 8 was the only one that would have been fail-open — and it was caught by an A/B probe before release, not by a user report.

    The verdict

    No fail-open leak path was found. Every perception failure degrades to the pre-perception baseline: blind redaction, DOM sweep, tokenizer, OCR, faces, and the zero-leak gate all still enforce in full. Perception is an additive backstop — nothing about the shipping guarantee depends on it running at all.

    One residual limit is documented and accepted rather than fixed. A photo-bearing element that lands in a tile the ViT reads as low-info blank gets no perception escalation. That is not a leak: face detection and OCR still operate on the region, and region redaction still applies when either fires. It is a redundancy limit — the two layers would have to be blind simultaneously — and it is exactly what the photo/blank separation measurement exists to surface.

    The tile distribution deserves a note too. That is the correct product outcome rather than a model failure: text PII on those surfaces is handled by the DOM sweep and OCR, never by the ViT. The score the eval actually reports is the photo/blank separation, which measures the signal the model is trusted to provide — 100% on the labelled-tile ground-truth page, with escalation firing on the photo cell and never on blank cells.

    What I did not measure

    An article like this is only useful if the gaps are as visible as the results. Three things remain open, and none of them are dressed up:

    • GPU-path latency on the same page. The benchmark harness runs headless Chromium without a WebGPU adapter exposed, so every latency figure above is a WASM-path figure. There is no side-by-side GPU-vs-WASM measurement on the same screenshot, and no per-operator partition data — which is also why the provider badge cannot be taken as a per-kernel measurement.
    • The memory growth curve over long runs. The shape of the cause is narrowed by the source even though the curve was never captured: the ORT session is a module-level singleton, created once and memoised, so per-step session churn is ruled out. There is no session.release() anywhere in perception.ts, and terminateVision() in vision.ts tears down the Tesseract worker and the face detector but leaves the ORT session and its WASM heap alive for the lifetime of the host context. The same-page cache is bounded at 6 entries, so it is not the leak either. What remains unmeasured is the growth rate of that single long-lived WASM heap.
    • The exact browser build that first exposed the WebGPU fallback. The fallback design is verified in code, but the original console capture from the environment that triggered it was not recovered, so this article does not claim a specific version, error string, or adapter state. Better to omit it than to reconstruct it from memory.

    The debugging playbook

    What survives from all of this, in the order I would actually apply it:

    1. Log the active execution provider per step, always. A silent fallback turns "why is it slow?" into a mystery. The provider label is session-scoped — it is the cheapest possible signal and it should never be optional.
    2. A/B every inference optimisation against a reference runtime. The batch bug was invisible in every local signal: no crash, no error, plausible confidences. It was only visible because onnxruntime-node was run on the same inputs and disagreed. Keep the tripwire (_abTest()) in the tree, not in a scratch script.
    3. Never let a backstop share a budget with the layers it backstops. Per-pass timeouts, not one shared deadline. Perception is best-effort; faces and OCR are not.
    4. Check that "corrupt" and "unsure" are distinguishable in your thresholds. Confidence bands are a design surface. A bug that lands in the uncertain band does not look like a bug — it looks like a cautious model, and it will happily escalate for safety while quietly destroying the signal you built the model for.
    5. Make escalation additive and prove it. A miss should cost performance, not privacy. Enumerate every failure point and ask the same question of each: does anything sensitive still travel?
    6. Measure first-run against cached separately. The cache is a latency optimisation; its correctness argument rests on the hash actually tracking visible change. Know exactly which samples it takes — luma, every fourth pixel, 64×64 — so you know which class of change it cannot see.
    7. Test the Chrome offscreen path and the Firefox background-page path separately. They share vision-host.ts and they fail differently.
    8. Write the failure catalogue down before the failure. The audit that produced the table above was committed in the same change as the perception stack, not written afterwards as a post-mortem. That is why rows 1–3 and 5–7 could be closed as "no fail-open" from source rather than from argument.

    Takeaways

    1. Surface the execution provider in the UI. Making WebGPU/WASM visible in the resource meter turned "why is it slow?" from a mystery into a screenshot. But report it honestly: it is a session-level label, not a per-kernel measurement.
    2. Bundle both runtimes. Shipping the .jsep build with a WASM fallback inside the extension means first-run latency never depends on a CDN, and fallback never depends on a network fetch.
    3. Verify across runtimes, not within one. The batch bug was found by disagreement between two implementations of the same maths, not by any signal inside either one.
    4. Design the failure path before the happy path. The guarantee that perception can fail without leaking came from enumerating nine failure modes and checking each one, not from being careful in the main path.
    5. Concurrency is a privacy control. Moving three passes from serial to Promise.all was a latency fix and a fail-closed fix at the same time, because it removed the mechanism by which the backstop could starve the primary layers.
